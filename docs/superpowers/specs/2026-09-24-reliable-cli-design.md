# PBHGEN Reliable CLI and Generation Design

## Goal

Complete the seven outstanding PBHGEN reliability tasks as a sequence of
independently reviewable changes. The result remains a general-purpose,
MIT-licensed PureBasic header generator while becoming deterministic and safe
for editors, build scripts, and multi-file projects.

## Compatibility boundary

The existing invocation remains valid:

```text
PBHGEN.exe source.pb
```

PBHGEN historically joins multiple unquoted command-line parameters so that an
IDE can pass a single path containing spaces. A new batch operation therefore
uses an explicit `--batch` option instead of interpreting every positional
parameter as a separate source:

```text
PBHGEN.exe --batch first.pb second.pb
```

The generated header format, default adjacent `.pbi` path, module behavior,
macro exclusion, PureBasic input, and SpiderBasic input remain compatible.

## Command-line contract

The supported forms are:

```text
PBHGEN.exe source.pb
PBHGEN.exe --batch source1.pb source2.pb [...]
PBHGEN.exe --check source.pb
PBHGEN.exe --check --batch source1.pb source2.pb [...]
PBHGEN.exe --output header.pbi source.pb
PBHGEN.exe --diagnostics json [other options] source.pb
PBHGEN.exe --version
```

`--output` is valid only for a single source. Options may appear before the
source arguments. Unknown options, missing option values, an empty batch, and
incompatible option combinations are usage errors.

`--check` generates the expected header in memory but does not modify disk. It
succeeds only when the destination exists and is byte-for-byte current. A
missing or stale header returns the dedicated stale exit code.

The process is synchronous: a successful exit means every requested header has
been fully generated, flushed, and installed or verified. Batch processing is
ordered exactly as supplied and stops after the first failure. Previously
completed files remain complete.

## Exit codes

PBHGEN returns these stable process exit codes:

| Code | Meaning |
| ---: | --- |
| 0 | Generation succeeded, or every checked header is current |
| 1 | `--check` found a missing or stale header |
| 2 | Invalid command line or unsupported option combination |
| 3 | Source, destination, or filesystem operation failed |
| 4 | Source could not be parsed into a safe declaration |

Every error path returns deliberately rather than falling through to a
successful process exit.

## Diagnostics

Human-readable diagnostics are the default and use this stable shape:

```text
path(line): severity CODE: message
```

Command-line diagnostics use line `0`. Parser failures report the physical
source line on which the declaration began. Codes are stable identifiers; the
initial families are `CLI`, `IO`, `CHECK`, and `PARSE`.

`--diagnostics json` writes one compact JSON object per source event. JSON Lines
is used so batch consumers can process results incrementally:

```json
{"source":"source.pb","output":"source.pbi","status":"ok","exit_code":0}
{"source":"bad.pb","line":12,"status":"error","code":"PARSE001","message":"Incomplete procedure signature","exit_code":4}
```

Strings are JSON-escaped. Diagnostic output is written only by console builds;
the exit code remains authoritative for IDE tool builds without a console.

## Generation pipeline

The current global parser flow will be separated into procedures with explicit
results:

1. Parse command-line options into an application configuration.
2. Read one source and retain physical line origins for logical statements.
3. Generate the complete header in memory.
4. Validate that every recognized procedure signature is complete and can be
   represented safely.
5. In check mode, compare the generated bytes with the destination.
6. Otherwise, write and flush a temporary sibling file, then replace the
   destination atomically.

This stays in `Entry.pb`; the project is not being converted into a framework
or full PureBasic grammar parser.

## Parser correctness and safe failure

Header prologue emission is separated from source-line parsing. This fixes the
existing defect where the first logical source statement is consumed only to
trigger the prologue and is therefore never parsed.

Each logical statement retains its original physical line number. A procedure
whose outer argument list never closes produces `PARSE001` and no destination
change. A recognized procedure keyword that cannot be converted into a
matching `Declare`, or a transformed declaration that fails structural
validation, produces a parser diagnostic instead of emitting `ERROR` or a
partial declaration.

Comments, ordinary strings, escaped strings, module separators, multiline
signatures, collection arguments, and typed pointers remain protected by
golden tests.

## Atomic and content-stable output

Generation never truncates the destination before parsing succeeds. The new
header is written to a uniquely named temporary file beside the destination so
the final replacement stays on the same filesystem.

If the destination already has identical bytes, PBHGEN removes the temporary
file and leaves the existing file untouched, preserving its timestamp and file
identity. If content differs, PBHGEN flushes and closes the temporary file and
uses the platform replacement primitive. A failed replacement leaves the old
destination intact and reports an I/O error. Temporary files are removed on
all handled failures.

The first verified implementation targets Windows. Platform-specific replace
operations are isolated behind one procedure so Linux and macOS behavior can
be added or verified without changing the parser.

## Tests

`tests/cli_tests.pb` is a public PureBasic black-box runner. It builds or invokes
PBHGEN, creates a uniquely named temporary workspace, enforces a finite timeout
on every child process, and verifies exit codes, output, timestamps, and JSON
diagnostics. The existing ignored PowerShell harness remains a local convenience
and is not committed.

New golden fixtures cover:

- a procedure as the first logical source statement;
- representative real-project multiline, quoted-default, typed-pointer,
  comment, module, and macro boundaries;
- an incomplete signature with an exact line-numbered diagnostic;
- single, output-selected, check, and batch CLI behavior;
- unchanged-output preservation and failed-generation preservation.

Each behavior is introduced red-first against the preceding implementation.
Every compile and child-process wait has an external finite timeout.

## Reproducible build and compatibility evidence

`scripts/build.pb` provides the documented build entry point. It requires an
explicit compiler path, uses fixed compiler flags, emits a console executable
to an explicit output path, applies a finite timeout, and records the PBHGEN
and PureBasic versions used. It does not bundle or modify a PureBasic compiler.

`COMPATIBILITY.md` records only configurations actually exercised. PureBasic
6.41 x64 on the current supported Windows environment will be the initial
verified row. Historical PureBasic 5.73 compatibility may be described as an
intent, but it will not be marked verified without running that compiler.

The PBHGEN public version remains `5.73` during this work. `--version` reads the
existing single version constant. Selecting a release version is intentionally
deferred until the completed matrix and changes are reviewed.

## Documentation and delivery

README usage will document the CLI contract, exit codes, diagnostic formats,
safe replacement behavior, reproducible build, and test commands. The private,
ignored `TODO.md` will be checked off as stages complete but will not enter
public commits.

The seven implementation stages are committed separately. No executables,
temporary output, local PowerShell runners, agent instructions, or TODO file
will be committed. Nothing is pushed, tagged, or published without an explicit
request.
